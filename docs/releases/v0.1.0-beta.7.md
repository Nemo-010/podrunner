A beta of podrunner, for tests. It is not for production CI.

podrunner runs each CI job of GitHub (or of another forge) in one fresh
unit and destroys the unit after the job. It needs no root and no
docker daemon. Each binary is static (musl).

## Quick start of the local mode

```sh
curl -fsSLO https://github.com/PodUtils/podrunner/releases/download/v0.1.0-beta.7/podrunner-install.sh
sh podrunner-install.sh
cd YOUR-PROJECT && podrunner run .github/workflows/ci.yml --checkout .
```

The installer downloads podrunner, podvm, podnet, the official runner and
the runner image, checks each SHA-256 against the pins of this release,
loads the image, and writes `run.toml`. A second run downloads nothing.
With no network: download `podrunner-bundle-ARCH.tar.gz`, unpack it, and
run `sh podrunner-install.sh --bundle .` in it (`docs/install.md`).

## What is new since v0.1.0-beta.6

* The installer and the offline bundle of the local mode (T-202, T-205).
  The release attaches the runner images (`runner-ARCH.tar`,
  `runner-full-ARCH.tar`) as assets that `podvm load -i` takes as they
  are (T-217).
* The findings of the first user run of the local mode (GitHub #153, #155
  to #167): `--platform` keeps the checks of the other flags; each refusal
  of an executor names its flag; `help`, `version` and `COMMAND --help`;
  `--validate` checks the needs; `--break` checks its job and step;
  `--local-repository` opens no relay; `doctor --run` names a wrong path,
  tries the loopback bind and reads each directory above the runner
  directory; each failure of a control verb names its path; `stop --wait`
  refuses a missing state directory; `mint-serve` names a file of `serve`;
  an unknown `--event` fails first (T-206 to T-219).
* A refusal of one source holds the job for that source only, not for
  each source of the host (T-222, githome's pair run on #151).
* The user-path gate (`user-gate.yml`): the files of this release,
  installed as a user with no root in four host classes, and a corpus of
  real projects; a release needs it green (T-243). Its first run found the
  faults of T-253 and T-254, fixed here: a link before its target in a tar
  of a checkout, a made-up `github.token` that real APIs refuse (the run
  now names `--github-token-env`), and directories of the installer that the group could write.
* The findings of the first adversarial QA (two agents with no context of
  the work, as users with no root on a host whose only egress is a proxy
  that intercepts TLS; T-246):
  * A checkout never holds `.secrets`, the files of `--secret-file`,
    `--env-file` and `--var-file` in the tree, or a lock file that is not
    committed; a symbolic link of a project file must stay in the project
    (T-268, T-275, T-276).
  * A job on `--runner-dir` takes `PATH`, the proxy variables and the CA
    files of the user, and gets a scratch `HOME`; a podvm unit with the
    network of the host takes the proxy and the CA files too (T-265,
    T-266, T-284).
  * A checkout of a git tree has a `.git` by default (`--no-git` leaves it
    out) (T-267).
  * SIGHUP cancels a run; a runner directory holds one run at a time, and
    one with a space in its path is refused (T-273, T-274, T-281).
  * On `--runner-dir`, a job with a Docker action fails before it starts
    (T-270); the dry run on `--podvm` refuses `services:`, and each runner
    image must be in the store (T-272); `--job` selects the jobs of a
    called workflow (T-271); each live line comes once (T-282); the
    refusals name better fixes (T-269, T-277).
* The findings of the second adversarial QA (T-246):
  * `github.api_url` and `github.graphql_url` of a job name the API of
    GitHub, as on GitHub (T-293).
  * A project `.actrc` keeps its files in the project; a project file that
    is a link out of the project, or that cannot be read, fails the run
    (T-292).
  * An empty `--github-token-env` variable reaches a job of
    `permissions: {}` (T-287); a Docker action of the tree is refused on
    `--runner-dir` (T-288).
  * A runner that a SIGKILL of podrunner left ends at the next run (T-294);
    `--microvm` checks `/dev/kvm` and its image first (T-297); a rerun
    keeps the end of a cell that its filter leaves out (T-295); each result
    line comes when its job ends (T-296); the dry run refuses a macOS cell
    (T-289).
* A `node20` action runs on Node 24, as on GitHub. On a host with a proxy,
  a job gets `NODE_USE_ENV_PROXY=1`, so the `fetch` of a Node action uses
  the proxy (T-299).
* `--microvm` works for a user with no root: each guest gets 8 GiB, as
  the initrd of the runner image needs more than 4 GiB (T-291). Proven in
  CI: user-gate 43877528216, lane `plain`.
* In a podvm unit, a program that closed descriptor 17 read the next file
  it opened there as empty, as podvm kept its memo on 17: a failing test
  suite of npm 6 passed, and Node read an invalid `package.json`. podvm
  `0.2.0-beta.26` checks the memo before each use (T-309, T-262).
* On the namespace rung of podvm, a podvm unit has a PID namespace and a
  `/proc` of its own (podvm `v0.2.0-beta.30`): a job does not see or
  signal the processes of the host (T-318). `doctor --run` says so, and
  names an older podvm. Proven on a constrained host as a user (no root,
  a proxy that intercepts TLS): a step saw 9 processes and could not
  signal a `sleep` of the user on the host; with podvm `v0.2.0-beta.27`
  it saw 98 and could signal it.
* `podrunner run .github/workflows/ci.yml` in a git tree gives that tree to
  `actions/checkout` with no `--checkout` (T-203).
* `doctor --run` checks the path of each flag; `--log-dir` is checked
  before the first job; under the hold a Node action takes the CA of the
  host (T-320 to T-322).
* Under the egress hold of `--podnet`, a job reaches its broker and no other
  port on the loopback of the host, so a proxy there is no way out (podnet
  `0.4.0-beta.13`, T-319). Proven on a constrained host as a user.
* `--podnet` takes the seccomp hold also on a host with user namespaces,
  so the egress hold of `run.toml` works there (T-302).
* On `--runner-dir`, the work directory has no name that starts with `.`:
  the `send` module of Node refuses such a path, and the runner directory
  of the installer is in `~/.local/share` (T-255).
* A unit that a destroy found with a process that had just ended reported
  an unknown count of processes (T-159).
* A podvm unit has the host name `podrunner-UNIT`, so the job log of
  GitHub does not show the host name of the host (T-182).
* The scale-set sidecar cancels the workflow run of a job that podrunner
  refuses (for example a tier mismatch or an untrusted owner), so a fork
  pull request does not hold the capacity of a trusted scale set (T-169,
  the ruling Q7 of the owner). The App needs the repository permission
  "Actions: read and write". A refusal for a wait deadline, a cancel or a
  conformance check does not cancel the run.
* A unit applies the limits of its offer: `memory`, `cpu` and `pids` of
  pod-job, the lesser of the offer and of `[unit.KIND]` (T-198). The
  podvm kind applies `memory` and `pids`, the incus kind all three; the
  microvm kind keeps the size of its guest.
* The report of a job comes before its `release`, also for a claimed job
  that could not start and for a job that a restart lost: at the
  `release`, a source knows whether podrunner refused the job. The source
  contract says how a job ends at the source (T-200).
* The job-started hook of the runner image writes an annotation that
  names the cause when it ends a foreign job (T-201).
* The findings of the fifth adversarial QA, each proven on a constrained
  host as a user (no root, a proxy that intercepts TLS, no KVM):
  * A job with containers that the executor cannot run (a runner
    directory, podvm with no container hooks, `services:` on podvm) is
    refused by that cause before the pin and the pull of its images, and
    the refusal names `podrunner doctor --run`; `--microvm` checks
    `/dev/kvm` before any pull (T-327, T-330).
  * Under `--podnet`, a failed job names the hosts that the hold refused,
    with the fix (`--allow HOST`); no line comes for each refused
    connection (T-328, T-329). A podvm unit asks no host of the package
    sources of the image before the job (`--no-source-fixup`, T-332).
  * The default checkout is the top of the git tree, or out of a git tree
    the project of the workflow file; with neither, the run is refused
    with the fix (T-336, T-337).
  * A dry run writes no state, and its JSON says `planned` (T-333).
  * A new run starts with no artifact of an earlier run in
    `--artifacts DIR` or `--state DIR`; `--state` with `--artifacts`
    keeps the artifact directory for `--rerun` (T-334, T-335).
  * `--no-cache`: `actions/cache` misses at once, with no retry (T-338).
  * `doctor --run` gives the scratch disk of the run (the image times
    `--jobs`); a full disk names `TMPDIR` and `--jobs`; a line names the
    unpack of the image at the start of a unit (T-325).
  * The base image has `make`, `python3` and `libatomic1` (Node 26 of
    `setup-node`) (T-324; proven in CI by `runner-image.yml`).
* podvm `v0.2.0-beta.30`, podcrates `v0.52.0`.

## What is proven in CI

* The tests of the sidecar against a fake scale set: the cancel of the
  run of a refused job, one for each run.
* On a podvm unit and an incus instance: a payload past `memory` and one
  past `pids` of an offer get an error, and the runner runs under the
  limits of a podvm unit.

## What is proven on a constrained host as a user

On the sandbox of the lead session (an egress proxy that intercepts TLS,
no KVM), on `--runner-dir`: `actions/setup-node` through the proxy with no
`--env`; a scratch `HOME`; `git` in a step with `--checkout .` only; a
SIGHUP during a job; a second run on a busy runner directory; a Docker
action refused in a dry run; each live line once.

The user-path gate (user-gate 43816078517 on `12a1300`), as a user with
no root in the lanes plain, small-tmp, userns-off, inherited-fds,
proxy-only and bind-denied, with the files of this release: the install
from the bundle and from a mirror, the quick start, `doctor --run`, and
`hello` on podvm and on a runner directory. On `--runner-dir` in each lane:
the rustfmt and docs jobs of BurntSushi/ripgrep, the Python 3.13 tests of
pallets/click, the lint and the Node.js 22 tests of expressjs/express, and
the lint of rq/rq (also behind a proxy that intercepts TLS). In a podvm
unit in each lane: ripgrep, and the Node.js 22 tests of express.

## What is not proven

* A real job of the local mode on a user host: the host of the first
  user run refused each loopback bind (T-220).
* The live gates (T-032, T-033, T-040) run on test hosts.
* The cancel of a refused run on github.com (GitHub #74, #121).
* On a host with no user namespace (H0), the runner timed out on the
  broker in the first live run (T-179).
* In a podvm unit, the tests of pallets/click (uv) and the lint of rq/rq
  (ruff) fail with EACCES at the persist of a temporary file: podvm does
  not map the path of a raw system call (T-261). They pass on
  `--runner-dir`. A podvm unit with a volume stays on the loader family
  until podvm binds the volumes of `run -d` (PodUtils/podvm#442).
* The base runner image has no C compiler: a build of a C extension
  fails there, also where the package has a fallback to pure Python
  (pallets/markupsafe: `Cannot update time stamp of directory ...`).
  Install with `--full` for such a project (T-326).
* A podvm unit off the namespace rung (the loader and supervise rungs, as
  on Ubuntu 24.04, where AppArmor restricts user namespaces) has no PID
  namespace: a job sees the processes of the host and can send a signal to
  each process of your user. `podrunner doctor --run` names the rung. For
  a job that you do not trust there, use `--microvm`.
* A podvm unit is not a boundary for a static binary where podvm runs it
  on the loader family (a host with no user namespace, and each unit with a
  volume in podvm `0.2.0-beta.30`): Go up to 1.20 in a job wrote into the
  home of the user on the host (T-300). Run untrusted jobs with
  `--microvm` or `--incus`.

## The files

| File | What it is |
| --- | --- |
| `podrunner-x86_64-unknown-linux-musl` | podrunner, Linux x86-64 |
| `podrunner-aarch64-unknown-linux-musl` | podrunner, Linux ARM64 |
| `scaleset-sidecar-x86_64-unknown-linux-musl` | the sidecar of a `github-scaleset` source, Linux x86-64 |
| `scaleset-sidecar-aarch64-unknown-linux-musl` | the sidecar, Linux ARM64 |
| `podrunner-install.sh` | the installer of the local mode, with the pins of this release |
| `podrunner-bundle-x86_64.tar.gz`, `podrunner-bundle-aarch64.tar.gz` | each file that the installer takes, for a host with no network |
| `runner-x86_64.tar`, `runner-aarch64.tar` | the runner image, for `podvm load -i` |
| `runner-full-x86_64.tar`, `runner-full-aarch64.tar` | the larger runner image (`images/runner/full.txt`) |

Each file has a `.sha256` file and a build provenance attestation.

```sh
sha256sum -c podrunner-x86_64-unknown-linux-musl.sha256
gh attestation verify podrunner-x86_64-unknown-linux-musl --repo PodUtils/podrunner
```

A unit also needs:

* podvm `v0.2.0-beta.30` (`images/podvm.toml` gives the SHA-256 of each
  binary); the `microvm` kind needs QEMU, and the `incus` kind an
  incusd;
* podnet `v0.4.0-beta.13` for the egress hold of the podvm kind
  (`images/podnet.toml`);
* the runner image: the asset `runner-ARCH.tar` (`podvm load -i`), or a
  build of `images/runner/Dockerfile`.
